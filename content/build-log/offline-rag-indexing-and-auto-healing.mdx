## 为什么线上动态切块与实时索引会拖垮服务

在早期的简易 Demo 中，开发者往往在用户发起请求或上传文档的一瞬间，调用嵌入 API 并同步切块写入数据库。在严肃生产环境中，这种做法极度脆弱：
一旦并发请求增多，或者嵌入模型 API 发生网络超时，正在执行的写入将产生大量半途而废的孤儿分块（Orphan Chunks），造成知识库数据严重脏读。

真正的工业级 RAG 必须拥有坚不可摧的**离线批量流水线与增量索引自愈机制**。

## 内容哈希指纹与事务性原子更新

鲁棒的离线索引流水线遵循以下准则：
1. **基于 SHA-256 的内容哈希 (Hash-Aware Incremental Sync)**：在切块前计算文章全文与单个分块的内容哈希。如果源文档没有发生变动，直接跳过昂贵的 Embedding 计算；
2. **数据库事务与影子表原子切换**：在大版本知识库全量重构时，数据写入临时影子表，索引全部校验完毕后在单个数据库事务内执行表名交换（Rename Table），实现线上零感知切换；
3. **周期性孤儿检查与自愈巡检 (Auto-Healing Cron)**：每日定时触发脚本，校验向量库中记录的 `post_id` 是否在文章主表中真实存在，自动清理历史废弃索引。

## 增量哈希变动感知算法

```js
import assert from "node:assert/strict";
import crypto from "node:crypto";
function isHashChanged(oldHash, newContent) {
  const current = crypto.createHash("sha256").update(newContent).digest("hex");
  return current !== oldHash;
}
const h = crypto.createHash("sha256").update("v1").digest("hex");
assert.equal(isHashChanged(h, "v1"), false);
assert.equal(isHashChanged(h, "v2"), true);
```
